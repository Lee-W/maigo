# Harness Discipline — Evidence Discipline

Loaded on demand by [`skills/harness-discipline/SKILL.md`](https://github.com/Lee-W/maigo/blob/main/skills/harness-discipline/SKILL.md) —
八個具體案例，共同主題是**證據必須獨立於嫌疑來源**：不能拿被懷疑的來源自己的輸出、
或自己的推測，來證明那個來源／推測是對的。Read this file when 你要斷言資料狀態、
判斷一個工具/log 是否可信、或要定罪某次改動造成的錯誤之前。

## 1. 別把推測寫成事實，先查 git 歷史核對

在文件、commit message 或對使用者的結論裡斷言「資料的狀態 / 來歷」之前——
**這張表是不是全新的、這個欄位一直都是這樣、這個檔案以前不存在**——
先查 git 歷史 / 實際狀態核對，不要把推測當事實寫下去。

**為什麼會錯**：在一次資產產生 PoC 裡，把「某個流程會建立並寫入**全新的**一張表」
當成事實寫進 PoC 文件、還準備 commit。使用者只問了一句「為什麼是全新的」，一查
git 歷史真相正好相反：那張表早就存在、裝著先前的歷史資料，是一次重構把寫入誤導去
了另一張表的 regression。憑直覺斷言，方向還反了；差一句追問就會帶著錯誤結論進
commit。

**具體做法**：

- 斷言「全新 / 不存在 / 一直都是 / 從來沒有」這類**資料狀態或歷史**的話之前，先驗：
  `git log -p --all -- <file>`、`git show <rev>^:<path>`、或實際 query 既有資料。
- 特別是會**進 commit 的文件**——錯誤一旦 commit 就變成專案的「事實記錄」，代價更高。
- 講不確定的事就標明「推測，未查證」，不要用肯定句包裝；使用者一句反問前，自己先反問。

## 2. 模糊 bug 回報先攤真實資料 / 要具體 repro，別連環猜假設

使用者回報一個模糊 bug（「X 會出錯」但沒講具體畫面 / 哪一筆 / 預期值）時，
**先把真實狀態攤出來**——跑實際指令、dump 現場資料、請使用者指著那一個案例說
「就這個」——再動手修。不要只靠讀 code 連續提假設去猜病因。

**為什麼會錯**：一次使用者只說「動作的內容會抓錯」，連環猜了好幾個假設，還寫腳本
掃 transcript 去否證，繞了好幾輪都沒中。真正解題是去跑 live 現場、把所有 session 的
實際輸出印出來、請使用者指認那一列——一指就定位（「抓到不同 session」＝跨專案歸屬
錯）。前面的假設驅動偵錯全是空轉。

第二次踩到（一個跨視窗跳轉的個人專案）：使用者只說「不同視窗的跳轉有一度抓不到」。
用系統腳本把現場狀態實際掃過一輪、已經握有具體異常（一個位置無效的視窗），卻還是
準備開 widget 問「當時顯示的是哪一種失敗訊息」——被一句「修吧」打斷。往下自己跑
對照實驗，很快就抓到可重現的真兇。

**具體做法**：

- 模糊回報先問自己：**我能不能現在就把真實輸出 / 現場資料叫出來？** 能就先做，讓
  使用者指認，而不是先開假設清單。
- 用 widget 丟「症狀選項」逼使用者選，往往不如直接攤 live 資料請他指認具體
  repro——後者一句話就收斂。
- **已經能自己實測重現時，連「症狀確認」都不要問，直接修**。攤 live 資料的目的是
  定位，不是換一種方式要使用者做筆錄；現場證據已經指向根因，就往下走。
- 假設驅動偵錯（讀 code 想原因）留到「真實資料已在手、需要解釋現象」時才用，不要
  在連現象都還沒看清前就空轉。
- **判準：手上的現場證據若已足以自己設計實驗，就別把回合交還給使用者。**

## 3. 判監控工具是否誤報，要取帶外真相，別拿它自己的狀態檔當「它正確」的證據

當回報是「**這個監控/狀態工具顯示錯了**」時，該工具自己的狀態檔／log／registry／
transcript **就是被懷疑漏訊號的那個來源**。用它來論證「工具其實是對的」是循環論證
——只是拿嫌疑犯的證詞替嫌疑犯背書。要下「工具正確」或「工具有 bug」的結論，必須取
**帶外（out-of-band）真相**：使用者現場畫面、實際 process 狀態、上游到底有沒有送出
事件。

**為什麼會錯**：一次使用者說「某個 session 應該在等我，但監控工具顯示跑完停著」。
讀了工具自己的 registry 與 transcript，看到最後是陳述句收尾、無懸空動作，就篤定
「工具沒壞、這就是正確的 idle」，還講得很有把握。使用者接著貼出現場畫面——正卡著
一個權限對話。證據全來自「被懷疑漏收事件的那條處理管線」，它當然顯示 idle。真正的
地面真相在使用者螢幕上，一句話就推翻了原本的判斷。（後來的正解是去查最原始的 raw
payload log 證明上游根本沒 fire 該事件，那才是帶外證據。）

**具體做法**：

- 聽到「工具顯示的狀態不對」→ 先分清楚：哪些資料**產自該工具本身**（不可拿來自證
  正確），哪些是**帶外**（可信）。
- 最快的帶外真相常常在使用者手上：直接問「你現在畫面上看到什麼」，比從 log 推半天
  更快、更準。早點問，別先築一座篤定的 log 論證。
- 要證「上游沒送訊號」用的是**記在任何處理之前**的 raw 層（如原始 payload log），
  而不是工具處理後的狀態檔——前者才獨立於被懷疑的處理邏輯。
- 這也是「自述／自產狀態不能自證」的同型（見第 7 節）：與第 2 節互補——那條講「先
  攤 live 資料」，這條補「攤的資料若產自嫌疑工具本身，就不算數」。

## 4. 分析會記錄自己活動的 log，用結構化欄位精確過濾，別用 substring

分析一份會**把你自己的活動也記進去**的 log（例如某監控工具的 payload log，會記錄每
次事件，包含你自己 session 的工具呼叫）時，用「你正在搜尋的那個字串」做 substring
過濾（`grep <id>`）會撈到**你自己剛剛下的除錯指令**——因為那些指令的文字裡就含著你
在找的 id。結果是把自己的事件誤當成目標的事件，產生假證據。改用**結構化欄位精確
比對**（`json.loads(line)['payload']['session_id'] == 目標_id`），排除文字碰巧含該
字串的行。

**為什麼會錯**：診斷一個問題時 `grep <session-id>` 撈 payload log，最後幾筆看起來是
某個時間點的事件——但那其實是**自己的 Bash 指令**（指令內容含那串 id，被 hook 記進
了自己 session 的 payload，又被 substring grep 命中）。差點據此推出錯誤時序。改用
`payload.session_id == FULL_ID` 精確篩後，真相才浮現。

**具體做法**：

- 過濾任何 observability / audit / hook log 前先問：**這份 log 會不會也記錄我自己
  此刻的除錯動作？** 會的話，substring 過濾必被污染。
- 一律用結構化欄位精確比對（解析 JSON 比對欄位值），不要 `grep <搜尋字串>`——尤其
  那個搜尋字串會出現在你自己下的指令裡。
- 這是「實測方法本身產生假證據」的一種：與第 2、3 節同源——證據的可信度取決於它是
  否獨立於「你自己」與「被懷疑的對象」。

## 5. 改動途中冒出的錯誤，先用舊碼在同一情境跑對照組再定罪

修 bug 途中冒出一個錯誤訊息時，直覺會是「大概是我剛加的那行造成的」，順手繞開。這
個直覺**一半的時候是對的，但錯的那一半會讓你把真兇當成自己的手滑放走**。定罪前先
做一件事：**把改動前的版本，在完全相同的情境跑一次對照組**——同樣的操作序列、同樣
的環境狀態。舊碼也噴 → 那是既有 bug（很可能正是要修的那隻）；只有新碼噴 → 才是自己
引入的。

**為什麼會錯**：修一個跨視窗跳轉的個人專案時，加了一行新的定位邏輯，跑出一個索引
錯誤，判斷是自己新加的那行造成的（那一次確實是），就移掉收工。後來把新腳本接上真實
流程再跑，同樣的錯誤又出現一次——這才拿**舊腳本**在同一情境（連續在兩個視窗間來回
跳）跑對照組：舊碼回程全掛、新碼全過。那個原本歸給自己手滑的錯誤，正是使用者回報
「有時抓不到」的真兇（位置型定位方式在順序變動時失效）。沒有這個對照組，會交出一
個「腳本更穩健了」但沒修到症狀的修正，還誤以為已經修好。

**具體做法**：

- 修改途中看到新錯誤 → 先問「**改動前會不會也這樣？**」，跑對照組再下判斷，不要靠
  直覺歸因。
- 對照組要**同情境**：同一組操作序列、同樣的前置狀態——對照組設計錯就會得到相反
  結論。
- 對照結果寫進 commit message 與 code comment，讓之後的人知道這行不是風格偏好、是
  有實測撐著的。
- 判定「已修好」的門檻是**舊碼會掛、新碼不掛**，不是「新碼跑得過」——後者只證明
  沒壞，沒證明有修到。
- 與第 2、3 節互補：那兩條講證據要獨立於嫌疑來源，這條講證據要有**時間軸上的對照**
  （改動前 vs 改動後）。

## 6. config 建議以真實 code/DB 為準，別信文件/範本

要給設定值（connection、環境變數、Variable 等）的建議時，**以真實來源為準**：

- 讀**實際執行的 code**，確認值是怎麼被拼接 / 使用的（不是猜，是看原始碼）。
- 查**既有的 DB 紀錄 / 現存設定**，沿用專案已建立的慣例。
- 文件 / 範本（`.env.template`、README）只當參考，**可能過時或誤導**，不可當權威。

**為什麼會錯**：部署某個外部 API / webhook 整合的 connection 設定時連錯兩次：
(1) 一開始沒看 DB，被要求「看 DB 裡既有的 connection 怎麼寫」，才發現同類 connection
有 `schema` + 純網域 host 的既有慣例；(2) 接著照 `.env.template` 註解寫，把 endpoint
路徑放進 Variable——但實際 code（一個只做 `base_url + endpoint` 拼接的 helper，
呼叫端只丟 `Variable.get()`）代表 endpoint 路徑必須放在 connection、Variable 只放
識別碼。文件那版反而誤導了判斷。

**具體做法**：

- 設定建議前先跑：找實際用到該設定的 code、讀它怎麼組值；用 CLI dump 既有同類設定
  當範例。
- 沿用既有慣例（同類 connection 怎麼拆 schema/host/endpoint）優於自創。
- 引用文件時加一句「以實際 code/DB 為準」，發現文件與 code 不一致時以 code 為準，
  並回頭修文件。
- 呼應第 2 節：先攤真實狀態再下結論，別靠假設。

## 7. 長跑 subagent 對「產物來源／歷史」的自述不可信，用 mtime / git 查證

長跑 subagent（工具呼叫多、token 高、中途 context 被壓縮）回報「這批檔案不是我
寫的／來源不明／開工前就存在」這類**來源與歷史**的敘述時，一律當作未經查證的說法：
用 `ls -lT` 的 mtime、`git status`、`git diff --stat`、mtime 是否落在該 agent 的執行
區間內來裁決，不採信敘述本身。

**為什麼會錯**：一次任務裡，一個實作型 subagent 跑了幾十次工具呼叫、token 很高，
中途被壓縮；完工回報時聲稱三個生產檔「開工前就已在工作樹、來源不明」。查 mtime 全部
落在它自己的執行區間內——是它自己寫的，只是壓縮後失憶。若當時採信「來源不明」，會
誤以為有平行 session 或殘留污染，白花時間追查，甚至可能把自己的正確產物當可疑東西
丟掉。

**具體做法**：

- subagent 一出現「來源不明／不是我做的／已經存在」的說法，先跑 mtime 與 git 狀態
  對照它的執行區間再下結論；同時把這視為「該 agent 的其餘自述也需獨立驗證」的
  訊號——產出者不驗自己，改派 fresh-context 驗證者複核。
- 與第 1 節同源：那條約束自己別把推測寫成事實，這條約束別採信別人的推測。

## 8. 單點觀測不足以支撐全稱結論——換一個會改變結果的觀測點來隔離

單一觀察點（一次建構成功、一次抽樣比對、一次 mutation 全綠）常被寫成全稱主張
（「一定可以」、「完全沒有交集」、「這樣就測到了」），但單點觀測只排除了「這一側」，
沒有排除「另一側」。判準：**換一個確實會改變結果的觀測點，看結論是否還成立**——
若換了之後結論翻轉，代表原本的單點觀測本來就沒有區辨力。

**Mutation canary 全綠有三種相反成因**，修法互相衝突，所以「全綠」本身不是結論，是
待分類的訊號：(1) 情境無區辨力——另一條路徑也會產生同樣的觀測值；(2) 斷言是套套邏輯
——沒有真的觀測到被測行為；(3) 該 mutation 觸及的分支根本不在任何測試範圍內。第 3
種最容易被誤判成「驗證通過」（因為指令 exit 0），也容易被反向誤判成「新斷言無效」。
隔離方法：換一個**確實會改變被測分支輸出**的 mutation 再跑一次；若那個轉紅，原
mutation 無感就屬第 3 種——原斷言有效，只是打在別的分支上。

實例（apache/airflow backfill partition preview）：`LimitedItemsList` 加
`orientation` prop 時，指定的 mutation 是把新加的 `data-testid` 從
`isVertical ? "…" : undefined` 改回無條件字串。跑下去五個測試檔全綠——因為該 gate
只影響 horizontal 分支，而 4 個 horizontal call site 從來沒有任何測試斷言過「truncate
到剩餘恰 1 筆」的 DOM。改用**反轉邏輯**的 mutation（`isVertical ? undefined : "…"`）
立刻轉紅，證明新斷言有效；「字面 mutation 無感」本身成為「該路徑無覆蓋」的證據，被當
發現回報，而不是被吞掉——若那個覆蓋洞落在 PR 之前就存在、本次未改變的行為上，正解是
回報並判定不在本 PR scope，不是補測試去填洞。

**第 1 種（情境無區辨力）的修法**：設計「只有被測分支能達成」的場景——通常是讓
**另一條路徑先跑完、且拿不到值**，逼結果只能由被測分支補上。這句是可獨立套用的
原則，不限於 React／`reset()`：後端的快取 fallback、API 預設值等任何「多條路徑會
收斂到同一觀測值」的情境，通常也適用同一個設計動作。下面的實例示範這個原則的具體落地。

實例（apache/airflow PR #71393）：`TriggerDAGForm.tsx` 有兩處寫
`partitionKey: suggestedPartitionKey ?? undefined`——一處在 `useForm` 的
`defaultValues`，一處在 `prefillConfig && open` 的 `reset()` effect。為後者寫的測試，
canary 把 effect 那處改回 `partitionKey: undefined`，8 個測試仍全綠——因為
react-hook-form 的 `reset()` 遇到 `undefined` 會 fall back 到 mount 時的
`defaultValues`，而 `defaultValues` 已經是同一個值，兩條路徑的觀測結果完全相同。修法
是把值改成「mount 之後才到達」：先 render 無建議值（`defaultValues` 因此捕捉到
`undefined`），再 rerender 帶建議值，只有 effect 能補上；canary 立刻轉紅，且這個場景
同時也是真實情境（API 查詢在首次 render 後才 resolve），不是為了測試硬造的。

**單點觀測寫成全稱／否定式全稱宣稱，一樣是同型錯誤**，只是發生在交辦與審查而非測試：

- 實作者測到 `OpenAIEmbedding(model="nomic-embed-text")` 建構失敗，寫成「embedding
  不可用、LLM 可用」；實際 `OpenAI(model="llama3").chat()` 一樣會炸，只是延後到首次
  呼叫才觸發——建構期驗證與呼叫期驗證是不同的觀測點，兩次抽樣剛好落在同一側，不構成
  全稱結論。
- 實作者測到「建構成功」，寫成「accepts any model name string」——同樣是把單點觀測
  當全稱。
- **審查者本人也會犯**：一份文件審查中，審查者做了兩個單點 membership 檢查
  （`gpt-4o` 不在 embedding 清單、`text-embedding-3-small` 不在 LLM 清單），據此宣告
  「兩份清單完全沒有交集」；實際交集有 `ada`/`babbage`/`curie`/`davinci` 四個舊名稱，
  它自承「沒有真的算過完整交集」。實作者事後實跑才推翻這個宣稱。

**具體做法**：

- 要回答「這樣就可用／全部情況都是這樣／兩者完全沒有交集」，先問「我手上的觀測點是不是
  剛好只覆蓋了一側？換一個會改變結果的觀測點會怎樣？」——真的換一個試，不要用同側再測
  一次來壯膽。
- 驗「某設定可不可用」要測到**實際使用那一步**（`.chat()`、真的送出、真的跑一次
  mutation 後的斷言結果），不是只測建構/初始化成功。
- 要回答「值域有哪些／某值存不存在／兩集合有無交集」，就真的算一次完整集合，不要用
  兩三個抽樣點推論。
- 否定式全稱（never / no way to / 完全沒有）最難證，通常要把主句收斂到與證據同範圍——
  證據只到 membership 抽樣，就只能寫「這幾個抽樣值沒有交集」，不能寫「完全沒有交集」。
- **審查者的結論同樣要被獨立重跑**——不要因為是審查者說的就照抄；本篇兩個實例都是靠
  「有沒有換一個會翻盤的觀測點」被抓到的。
