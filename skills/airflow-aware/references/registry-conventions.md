# Airflow provider registry conventions (`dev/registry/`, `registry/`)

Loaded on demand by `skills/airflow-aware/SKILL.md` §10 and
[`references/review-checks.md`](https://github.com/Lee-W/maigo/blob/main/skills/airflow-aware/references/review-checks.md) —
apache/airflow's Provider Registry site (https://airflow.apache.org/registry/)

when a diff touches `dev/registry/` or `registry/`, or when a `provider.yaml`
change needs to propagate to the registry site.

## Overview: two-sided architecture, one source of truth for module types

The Airflow Provider Registry is **not** an external service — its source
lives in-repo, split across two layers:

- `registry/` — the front-end: an **Eleventy (11ty)** static site (own
  `.eleventy.js`, `pagefind.yml`, `package.json`/`pnpm-workspace.yaml`).
  Provider page + module-category tabs live in
  `registry/src/provider-version.njk` (a `{% for t in types %}` loop over
  generated data). Deployed by `.github/workflows/registry-build.yml`.
- `dev/registry/` — the **Python source-of-truth + extraction** layer. It
  reads `provider.yaml` files directly (not via `get_provider_info`).

**Single source of truth for module categories**:
`dev/registry/registry_tools/types.py`'s `MODULE_TYPES` dict
(operator/hook/sensor/trigger/transfer/bundle/notifier/…, now also
`toolset`) — each entry carries `yaml_key`, `level`, `suffixes`, `label`,
`icon`; base-class detection lives in `BASE_CLASS_IMPORTS`.
`registry/src/_data/types.json` is a **generated artifact**, regenerated by
`dev/registry/generate_types_json.py` — never hand-edit it; drift is
enforced by `scripts/ci/prek/check_registry_types_json_sync.py`. Module
extraction (`modules.json`, `issubclass` type detection) runs via `breeze
registry extract-data --provider <p>` → `dev/registry/extract_parameters.py`;
`dev/registry/extract_metadata.py` only builds `providers.json` and does
**not** build modules. `modules.json` is gitignored. Icons are single
characters (`test_icons_are_single_character`) and must be unique across
types. To add a category end-to-end: `MODULE_TYPES` + regenerate
`types.json` + the `provider.yaml.schema.json` section + the provider's
`provider.yaml` + the completeness check (the `check-provider-yaml-valid`
prek hook — run from `providers/`, see this skill's SKILL.md §3).

**Search is two independent implementations — a search-behavior change
means checking both** (getting this wrong cost a scope miscall on PR
#70498):

1. The filter box on `/providers/` — `#provider-search` →
   `registry/src/js/provider-filters.js`, a plain browser IIFE doing
   substring matching over `data-*` attributes rendered by
   `registry/src/providers.njk`.
2. The global modal (header magnifier, `Cmd+K`, home-page hero) —
   `#search-input` → `registry/src/js/search.js`, backed by **Pagefind**.
   Its records come from `registry/scripts/build-pagefind-index.mjs` via
   `addCustomRecord` only — **Pagefind never indexes the page HTML here**,
   so adding a `data-*` attribute does nothing for it, and grepping for the
   first search's symbols won't surface the second.

A third, unrelated search (`provider-detail.js`) filters modules within one
provider page. Matching logic is also split across build time and runtime:
`registry/src/_data/providerKeywordMatch.js` (CommonJS, build time) and the
IIFE in `provider-filters.js` each carry their own copy of `normalize()` —
the browser can't `require` the module, so the two copies are kept in sync
by hand, not by sharing code.

## 10.13 registry `slice`/`first` cutoffs need a sort key *(Request changes)*

**Scope gate**: only applies when the diff touches `registry/src/*.njk`
templates, or the `_data/*.js` layer feeding them.

Any `| slice(0, N)` (or `| first` / `[:N]`) truncation in a registry template
must be preceded by an explicit sort — sort in the `_data/*.js` layer, not the
template (nunjucks' `sort` filter doesn't accept a dotted attribute path, so
sorting there requires flattening first, which is more code for the same
result). Widening the membership of the collection feeding a slice — a
broader match condition, an added keyword, a new data source — is a silent
regression if the cutoff isn't sorted: known providers can drop out of a
badge/top-N list with no test or build failure to flag it, only a visual
discrepancy on the built page. When reviewing a change that widens any
collection with a downstream slice, grep that collection's consumers for a
truncation point and require a sort key as part of the same change, not a
follow-up.

## 10.23 registry class-level module `category` string is not user-visible — don't confuse it with the type `label` *(narrow — only applies to `dev/registry/` or `registry/` diffs, Request changes)*

**Scope gate**: only applies when a diff touches `dev/registry/` or
`registry/`.

In `registry/src/provider-version.njk` (the provider-version page), each
module entry's `category` field is used in exactly one place:
`data-category="{{ module.category }}"`, an HTML attribute never rendered as
visible text. The sidebar's "Categories" filter list (`pv.provider.categories`,
`cat.id`/`cat.name`) is built only from `provider.yaml`'s `integrations` list,
via `extract_integrations_as_categories` in `dev/registry/extract_metadata.py`.
Class-level (FQCN) sections — notifications/secrets-backends/logging/executors/
extra-links/queues/auth-managers/db-managers — have no matching integration, so
their `category` string never appears as a clickable filter option and is
never seen by a user.

**How to apply**: when a diff renames a class-level section's category-related
string (as in apache/airflow#70190, which renamed the `queue` type's
user-visible **label** from "Queues" to "Message Queues"), first identify
which string is being changed:

- `MODULE_TYPES[...]["label"]` — the user-visible type label shown on the
  module-type tab. Renaming this is a real UI change.
- The internal `category` string (`CLASS_LEVEL_CATEGORY_OVERRIDES` or its
  yaml-key fallback) — only a `data-*` attribute value. Renaming this has
  **no** visible effect on the page.

Flag a PR that renames only the internal `category` string, believing it
changes user-facing text, as a no-op relative to its stated intent — point
the author at `MODULE_TYPES[...]["label"]` instead.

## New `provider.yaml` `connection-types` sub-field: 8 touchpoints, two data paths (narrow — read only when this applies)

**Scope gate**: only applies when a diff adds or renames a `connection-types`
**sub-field** (e.g. `external-services`) on a `provider.yaml` connection
type — not a new connection type itself.

Adding or renaming a sub-field touches 8 sites (2026-07-31, PR #70497 —
reviewer kaxil caught two of them missed on the first pass):

1. `airflow-core/src/airflow/provider.yaml.schema.json` — the schema key
   and its `description`.
2. `providers/<provider>/provider.yaml` — every connection-type entry that
   uses the field.
3. `providers/<provider>/src/.../get_provider_info.py` — **generated, never
   hand-edited**; regenerate with `prek run update-providers-build-files
   --files <provider>/provider.yaml` from `providers/` (see the provider.yaml
   regen-scope recipe in
   [`references/review-checks.md`](https://github.com/Lee-W/maigo/blob/main/skills/airflow-aware/references/review-checks.md)).
4. `dev/registry/extract_metadata.py` — the **latest-version** extraction
   (reads the hyphenated key, writes the underscore key).
5. `dev/registry/extract_versions.py` — the **per-version** extraction.
   **The single easiest one to miss.**
6. `dev/registry/registry_contract_models.py` — the `ConnectionTypeContract`
   Python field (`extra="forbid"`).
7. `registry/src/provider-version.njk` — reads the underscore-cased field
   name plus its own local variable.
8. `contributing-docs/23_provider_hook_migration_to_yaml.rst` — the only
   place a provider author learns which `connection-types` sub-fields
   exist; add a `~~~~`-underlined subsection, ordered to match the schema's
   key order.

**Why two of them independently**: `registry/src/provider-version.njk`
branches on `pv.isLatest` into **two separate data paths** — the latest
version reads `pv.provider.connection_types` (from `extract_metadata.py`),
every other version reads `pv.versionData.connection_types` (from
`extract_versions.py`). Populating only `extract_metadata.py` looks correct
while the edited version is still latest, then the table **silently
disappears** the moment a newer version supersedes it — no test or build
goes red. `dev/registry/extract_connections.py` is a *third* place
`connection_types` gets produced, but it feeds the conn-builder panel
(`ProviderConnectionTypeContract`, which doesn't render this kind of field)
— don't add it to the checklist by mistake.

**How to apply**: walk the 8 sites as a checklist, confirming site 5
separately. After editing, grep the whole repo for the **old** field name
with a precise alternation (`<name>|<snake_name>|<camelName>|<CamelName>`) —
not a loose wildcard like `external.integrations`, which false-hits
unrelated English prose (`airflow-core/docs/core-concepts/objectstorage.rst`,
`dev/breeze/doc/ci/05_workflows.md`). On the test side, feed both
extractors' output through the contract validators
(`validate_providers_catalog` / `validate_provider_version_metadata`) —
`extra="forbid"` ties the YAML key, the extracted JSON key, and the
contract field name together; the `.njk` template side isn't covered by
that, so verify it with the "registry frontend has zero automated
verification" recipe below.

## New provider.yaml module section: registry + validator touchpoints (narrow — read only when this applies)

**Scope note**: this only applies when a diff introduces a brand-new
`provider.yaml` **module-section type** — a new category alongside
`sensors`/`operators`/`hooks`/`triggers`/`bundles`/`toolsets` — not a new
entry under an existing section. This is rare enough not to warrant a
standing numbered checklist item; read this recipe when it comes up.

The change spans two subsystems, and one of them can turn CI red if a new
section is added to the wrong list:

- **Registry side**: `dev/registry/registry_tools/types.py`'s `MODULE_TYPES`
  (source of truth: `yaml_key` / `level` / `suffixes` / `label` / `icon`) plus
  its base-class import list; `registry/src/_data/types.json` (generated,
  drift-checked); CSS in `tokens.css` (a `--color-<type_id>` token) and **five**
  `main.css` rule families, not just one — `.tab-icon`, `.type-icon`,
  `.share-bar`, `.provider-card .modules`, and
  `.provider-detail-page .modules .module .icon`. Missing CSS doesn't error —
  the badge silently falls through to the bare base rule with no background.
  Note the two naming conventions: the registry type id uses underscores
  (`retry_policy`), the `provider.yaml` key uses hyphens (`retry-policies`);
  CSS uses the type id.
- **Validator side** (`scripts/in_container/run_provider_yaml_files_check.py`):
  four hardcoded section lists exist, and they are not equally safe to
  extend — check `check_duplicates_in_integrations_names_of_hooks_...` and
  the `registered_modules`/`check_invalid_integration` call sites are safe to
  add to; a fifth touchpoint pair (`base_class_resource_map` and the
  `registered_modules` tuple) both need the new `(<BaseClass>, "<yaml-key>")`
  entry — missing either leaves class-registration unchecked for the new
  section.

**The trap**: `check_correctness_of_list_of_sensors_operators_hook_trigger_modules`
runs a completeness assertion whose glob is `**/{resource_type}/*.py` — it
assumes the module lives in a directory *named after the resource type*. If
the new section's modules don't (e.g. a hypothetical `retry-policies` module
living under `policies/retry.py` rather than `retry-policies/`), adding it to
this list turns CI red with `Items in the right set but not the left`. In
that case, write a new existence-only `@run_check` function instead (shape:
`check_hook_class_name_entries_in_connection_types`, collecting
`python-modules` with `ObjectType.MODULE`) — and register it in the
unconditional call sequence, not inside `if all_files_loaded:` (that block
only runs on a full scan; a scoped single-file validation run would silently
skip the new check and report a false green). "Yaml key ≠ directory name" is
not unique to a hypothetical new section either — `secrets-backends` modules
already live under `secrets/`, not `secrets-backends/` — so don't describe
the directory-matches-key pattern as universal in a comment or PR
description.

This whole scenario is a worked example of the
[`change-site-enumeration`](https://github.com/Lee-W/maigo/blob/main/skills/change-site-enumeration/SKILL.md)
skill's "shared constant changes tuple arity/field count" row — grep the
constant name (`MODULE_TYPES`, the hardcoded section lists), not the type
name, and re-grep after the change to confirm no further site remains.

**Not everything with a type id needs a CSS entry — `#search-results`'s
per-type selectors are a deliberate exception, not a sixth family to
add.** `#search-results a.<id>` has **zero** CSS across all 19 existing
type ids — that's the consistent current state, not a backlog of missed
entries, so don't flag it or "fix" it when adding a new type.

**`icon` used to be derived independently in two other places, not read
from a single source.** Before PR #70190's fourth review round,
`provider-version.njk`'s module card and `registry/src/js/search.js`'s
search results each computed a type's icon letter themselves (first letter
of the type id) instead of reading `MODULE_TYPES`'s curated `icon` —
so changing `icon` in `MODULE_TYPES` and regenerating `types.json` did
**not** change what those two screens showed. Concretely: recoloring
`db_manager`'s curated letter to `M` left the module card still showing
`D`, colliding visually with `decorator`/`dialect`. The fix added a
`typeIcon` filter to `.eleventy.js`, and had `search.js` read an
additional `typeIcons` map off `#types-data` (the same `base.njk`-injected
data it already parses) — after that, both screens derive the letter from
the same source `MODULE_TYPES` feeds, and changing `icon` today only needs
`MODULE_TYPES` + a `types.json` regen. If a *new* screen is added that
displays this icon, make it read the filter/map too — don't let it start
deriving the first letter on its own again.

**CSS values use the `rgb(from var(...))` alpha syntax, never a hand-copied
hex literal.** New CSS lines for a type's color take the form
`rgb(from var(--color-<id>) r g b / 0.2)` to get an alpha variant —
`registry/CLAUDE.md` explicitly forbids hardcoding color values, and a
hand-copied `rgba(...)` literal silently falls out of sync the next time
the token's value changes. This isn't hypothetical: `--color-db_manager`
itself was later changed because it collided visually with
`--color-retry_policy`.

**This exact miss has already recurred twice.** PR #70122 (`toolset`) and
PR #70499 (`retry_policy`) each shipped missing the same three `main.css`
families; neither was caught until PR #70190's fourth review round, when
reviewer kaxil brought coverage from 6/19 to 19/19 in one pass. Treat a new
module type's CSS coverage as a checklist to walk explicitly, not
something a first read-through reliably catches.

## `provider.yaml`'s `ui-field-behaviour`/`conn-fields` override the hook's `get_ui_field_behaviour()` entirely (narrow — read when a diff changes connection-form UI text)

**Scope note**: applies when a diff changes a connection type's user-visible
field text (placeholder, label, hidden fields, external-services) by editing
a hook's Python methods.

`ProvidersManager._import_hook` first computes `ui_metadata_loaded =
conn_config is not None and bool(conn_config.get("conn-fields") or
conn_config.get("ui-field-behaviour"))`, and only falls back to the hook's
`get_connection_form_widgets()` / `get_ui_field_behaviour()` when that is
**False**. Once a connection type's `provider.yaml` entry declares
`conn-fields` or `ui-field-behaviour`, the hook's same-named Python method
becomes dead code — every placeholder, relabeling, and hidden-field the
connection UI (and the provider registry) shows for that connection type
comes from `provider.yaml`.

**How to apply**: to change a connection type's user-visible field text,
treat `provider.yaml` as the only source of truth — edit it, then run `prek
run update-providers-build-files --files providers/<p>/provider.yaml` to
regenerate `get_provider_info.py` (a generated file — never hand-edit it).
The reverse also applies when checking whether a stale claim has been fully
cleaned up: enumerate `provider.yaml` alongside the hook source and docs —
grepping only the hook's Python file and docs misses the file that actually
drives the UI. Case study: apache/airflow#72013 (fixing `LlamaIndexHook`'s
false claim of Ollama/vLLM support) initially edited only the docs and
`hooks/llamaindex.py`'s `get_ui_field_behaviour()`; review caught that the
connection UI and provider registry both read `provider.yaml`, so the edited
method was dead code and the false claim was still user-visible.

## `external-services` list membership: what counts as reachable *(narrow — read when reviewing/writing a connection-type's `external-services` field)*

`providers/common/ai/provider.yaml`'s `external-services` field renders into
the registry page as "which upstream services can this connection reach" —
a factual claim to the reader, not a style choice. Judgment (2026-07-31,
PR #70497, reviewer kaxil):

- **Counts**: any vendor the hook actually **instantiates** on its
  `get_llm()` / `get_embedding_model()` / provider-resolution path; and
  anything reachable purely through the connection's own fields (`host` →
  `api_base=`/`base_url=`) pointed at an OpenAI-compatible endpoint —
  Ollama, vLLM, LM Studio are this shape (same `OpenAI` class, different
  endpoint).
- **Does not count**: a vendor the hook's own docstring says to
  instantiate yourself and pass to the operator's `llm=`/`embed_model=` —
  that path **completely bypasses** the hook and the connection.
  `LlamaIndexHook`'s docstring named Cohere / AWS Bedrock / Google Vertex AI
  / HuggingFace this way, and all four were originally listed anyway.
- **Depends**: a hook with an env-var fallback (`PydanticAIHook` has one)
  can still legitimately list a vendor whose connection fields don't fully
  cover it — AWS Bedrock needs `region_name` etc., beyond `api_key`/
  `base_url`, and the reviewer accepted it on exactly that basis.

**Why this is easy to get backwards**: the same vendor name in a docstring
can mean either "this hook supports it" or "this hook doesn't — bring your
own instance," and grepping for the vendor name or skimming the docstring
summary reads the second as the first.

**How to apply**: read the hook source for the actual `import`/instantiate
target (e.g. `hooks/llamaindex.py` only imports
`llama_index.llms.openai.OpenAI` and
`llama_index.embeddings.openai.OpenAIEmbedding`), then trace
`_connection_kwargs`-style code to see which connection fields become which
kwargs. Keep one vendor's spelling consistent across every connection type
that lists it (`Mistral` vs `Mistral AI` reads as two different upstreams in
the same table otherwise). See also
[`references/docs-conventions.md`](https://github.com/Lee-W/maigo/blob/main/skills/airflow-aware/references/docs-conventions.md)'s
"Label an upstream-driven subset as representative, and link the full list"
— the same PR round applied both: get the *membership* right (this
section), and *label it correctly* once it's an open set (that one). After
editing `provider.yaml`, regenerate `get_provider_info.py` — don't hand-edit
both; see the connection-field touchpoints section above and the
provider.yaml regen-scope recipe in
[`references/review-checks.md`](https://github.com/Lee-W/maigo/blob/main/skills/airflow-aware/references/review-checks.md).

## Guide-link has two doc readers — working tree and git tag (narrow — read when changing registry Guide-link behavior)

The module card's "Guide" link is derived by
`dev/registry/registry_tools/docs_guides.py` from a provider's own
`docs/*.rst`, fed by **two independent entry points** into the same
`collect_guide_anchors`:

- `dev/registry/extract_parameters.py`'s `read_guide_docs(docs_dir)` — reads
  the **working tree** (the latest version).
- `dev/registry/extract_versions.py`'s `read_guide_docs(tag, layout,
  dir_path)` — reads a **git tag** (a superseded version, built only from
  its own per-version metadata).

A Guide-link behavior change needs both updated — touching only one leaves
the latest version's anchors out of sync with every historical version's.
Both share the same page filter, `is_guide_page(relative_path)`, in the
same file.

Verified facts that are easy to get wrong (2026-09-18, PR #71477):

- **`_api/` is gitignored (`.gitignore:219,296`) but is still built into
  real pages.** `devel-common/src/docs/provider_conf.py:153-160`'s
  `exclude_patterns` only excludes `operators/_partials` and a couple of
  `_api/.../index.rst` files — every other autoapi module page still gets
  built. So "underscore prefix ⇒ never becomes a page" is wrong; the actual
  reason to skip these is (a) gitignore means the working-tree reader sees
  them only on a tree that's already been built, while the git-tag reader
  never can, and (b) `_` (ASCII 95) sorts before lowercase letters (97), so
  it wins first-page tie-breaks in `sorted(docs)`.
- **`_partials` isn't only under `operators/`** — `providers/amazon/docs/_partials/`
  is top-level, and `exclude_patterns`'s literal string doesn't cover it.
  Write the filter as "any path part starting with `_`, at any depth," not
  a fixed prefix.
- **`changelog.rst` / `commits.rst` are real pages** (they're in the
  provider `index.rst`'s toctree), not generated artifacts. That they don't
  currently produce an anchor is a content coincidence (the inline literal
  in `providers/amazon/docs/changelog.rst:24` isn't followed by an
  underline decoration on the next line) — not a structural guarantee.
- A guide section that documents both an operator and its decorator in one
  heading (e.g. ``AgentOperator`` & ``@task.agent``, or
  `snowflake/docs/decorators/snowpark.rst`'s ``@task.snowpark``) needs the
  title match to take **the leading literal only**, not the first literal in
  the heading — the catalog really does have a module named `@task.agent`.

Tests live in `dev/registry/tests/`:
`uv run --directory dev/registry --group dev pytest tests/ -q` (CI form:
`cd dev/registry && uv run --group dev pytest tests/ -v`,
`.github/workflows/registry-tests.yml:64`).

## Registry cards use concepts that hold for any provider, not one provider's vocabulary

The registry (`registry/src/provider-version.njk`) is shared by every provider. When adding a card,
the title and concept must hold for a second provider: for example one **External services** card
whose rows each name their source type (Connection / Toolset), rather than a card for a concept
only one provider has (Toolsets, declared only by common.ai at the time). On apache/airflow #72940
a maintainer asked for "a more generalized solution", and the fix merged the Toolsets card and the
per-connection external-services sub-table into one generic External services card.

## Before rendering a `provider.yaml` field in the registry or docs, confirm schema and real data

Check two things first: (1) `airflow-core/src/airflow/provider.yaml.schema.json` defines the field
— many sections are `additionalProperties: false`, so an undefined field cannot be filled in and is
rejected by `check-provider-yaml-valid`; (2) at least one real `provider.yaml` fills it in.
Screenshots made by injecting fake data into the gitignored generated JSON only prove that the
template can render, not that a real build will show anything; mark in the PR description and
screenshots which parts are fake data.

Case (apache/airflow #72940): the extractor read `toolsets[].external-services`, but the schema's
`toolsets[]` only had `integration-name` / `python-modules` with `additionalProperties: false`, and
no `provider.yaml` filled it — so the Toolsets card would never render in a real build, while the
PR screenshot (a provider "with toolset") used fake data. The field and data came from #72939.

## Registry frontend has zero automated verification — verify by hand instead

`registry/`'s front-end (`src/js/*.js`, `*.njk`, `src/css/*.css`) has **no
automated verification** in this repo (2026-07-31):

- `registry/package.json` only declares `dev` / `prebuild` / `build` /
  `postbuild` — no lint, no test.
- No `*.test.js` / `*.spec.js` / vitest / playwright config exists anywhere
  in the tree.
- The only registry-related prek hook is `check-registry-types-json-sync`
  (keeps `types.json` in sync with `types.py`) — nothing checks
  `registry/src/js/*.js` or `*.njk`, and there's no eslint/stylelint/prettier
  either.

The one thing that does run automatically, `cd registry && pnpm build`
(exit 0, ~955 files + a Pagefind index), only proves the produced **HTML
structure** is well-formed — it says nothing about JS behavior after the
page loads (class toggling, focus, event ordering).

**Two traps that manufacture false conclusions** (2026-07-31, PR #70497):

- `registry/src/_data/providers.json`, `modules.json`, `search-index.json`,
  and `versions/**` are **gitignored local caches**
  (`.gitignore:303-308` — only the 12 tracked `.js` loaders and `types.json`
  in that directory are tracked); CI regenerates them from `provider.yaml`
  via `dev/registry/extract_*.py` before every build. So renaming a field
  and immediately running `pnpm build` shows **stale data against the new
  template** — a table disappearing is a false negative, not a broken
  template. **Judging a single file's tracked-vs-gitignored status from a
  directory-level `git ls-files` is itself a trap** — a 2026-08-04 second
  review round misread a directory listing (which surfaced the 12 tracked
  loaders) as proof `providers.json` was tracked, then proposed
  `git checkout -- <file>` as the fix — which fails outright on an
  untracked path. Check a single file with `git check-ignore -v <file>` or
  `git ls-files --error-unmatch <file>`, never infer it from the directory.
- `pnpm build`'s `prebuild` only runs
  `dev/registry/export_registry_schemas.py`, which derives an OpenAPI JSON
  Schema from the Pydantic model by pure introspection — it never
  instantiates the model against real data, so `ConnectionTypeContract`'s
  `extra="forbid"` never actually engages on this path. **A green build
  proves the 11ty template syntax is valid — nothing about whether the data
  and the template agree on field names.**

**How to apply**: to verify a data-field-name change, patch the local cache
into the post-extraction shape first — back up
`registry/src/_data/providers.json` to a scratchpad copy, edit the key with
a small Python script, build, assert against the result, then restore and
**verify by `sha256sum`, not exit code alone** (macOS's `cp` is often
alias'd to `-i` and silently no-ops the restore). To verify a *behavior*
change, write acceptance in two layers: (1) `pnpm build` exit 0 plus a grep
assertion against a real produced page (e.g.
`registry/_site/providers/amazon/9.32.0/index.html`); (2) for anything
dynamic, a table mapping "behavior → the `file:line` that guarantees it,"
explicitly labeled "not browser-tested." To actually see it, `pnpm dev` and
open `localhost:8080` (the main worktree already has `node_modules`; a
fresh worktree does not — see
[`references/verification-tooling.md`](https://github.com/Lee-W/maigo/blob/main/skills/airflow-aware/references/verification-tooling.md)'s
"A fresh worktree has no UI `node_modules`" section). A first blind fix
attempt is fine; a second miss in the same spot means stop guessing and
get real eyes on it, not a third guess.

**Backfilling one provider into the local cache** (2026-08-24: a
newly-added `providers/anthropic/` existed on disk, but the local
`providers.json` still only had an old fixture's 2 providers, so search
found nothing — the root cause was missing data, not search logic):

```bash
uv run --project dev/registry python dev/registry/extract_metadata.py --provider <id> --allow-unreleased
```

`--provider <id>` re-extracts only that one provider and merges it into the
existing `providers.json`/`modules.json` (no full rebuild). `--allow-unreleased`
is needed because a newly-added provider usually has no
`providers-<id>/<version>` git tag yet, and without the flag it gets
filtered out. Follow up with `node scripts/build-pagefind-index.mjs` to
rebuild the search index — eleventy's `--serve` watch mode doesn't rerun it
automatically. To confirm a provider is actually present in the local data
before debugging search logic:
`python3 -c "import json; print([p['id'] for p in json.load(open('src/_data/providers.json'))['providers']])"`.

A no-install manual technique — connecting to an already-installed browser
over the raw DevTools Protocol from a plain script — can also close this
verification loop for client-side JS behavior (e.g. confirming a search
actually returns the right results) without pulling in puppeteer or
playwright.
