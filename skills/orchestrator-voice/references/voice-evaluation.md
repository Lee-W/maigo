# Voice Evaluation — 固定情境與盲評

Read this file when 修改角色 prompt、交棒轉述或旁白，或比較新舊聲音的辨識度。
由 [`orchestrator-voice`](https://github.com/Lee-W/maigo/blob/main/skills/orchestrator-voice/SKILL.md)
與 [`narration`](https://github.com/Lee-W/maigo/blob/main/skills/narration/SKILL.md) 載入。
這是人工評讀的案例與判準；例句、文件建置與關鍵字檢查都不構成模型實測成績。

## 先固定實驗條件

- 記錄 source commit；有未 commit 的修改時，保存實際 source snapshot 與雜湊。
- 記錄宿主版本、模型／權重版本、推論設定、載入的檔案、輸入卡、原始回覆。每次改 prompt
  就分開記錄；新舊版本用相同情境與設定比較。
- 宿主允許時明確指定模型；逐筆核對回覆 metadata 的實際模型。預設值漂移或 fallback
  換模型時，保留原稿但排除於同模型比較，固定設定後重跑受影響樣本；不能只記請求值。
- 開新 session，由準備者將待測 snapshot 的角色檔與 `role-handoffs.md` 內容附進 prompt；
  旁白則附 `narration/SKILL.md`。不沿用安裝快取或原 session 開場時的舊 prompt。
- 先分別評角色短句，再評主線轉述。前者有特色、後者只剩「完成」時，問題在轉述層。
- 純聲音案例不需連網、改檔、執行測試、讀私人 memory 或啟動其他 agent；卡片的 output
  是**模擬紀錄**。另用實際工作流 trace 驗證工具行為，兩種證據分開標示。

## 給生成者的任務

每張卡、每個角色各取一份回覆；同一輪不讓模型看到其他角色的答案。五位工作角色與兩位
旁白都可比較，但旁白只做 narration 容許的框場，不安排自己動手修或驗證。

```text
請依本次 prompt 隨附的角色／旁白定義，針對下方模擬紀錄寫一至兩句對使用者的回報。
這是聲音測試，不執行工具、不補造執行紀錄，也不需要輸出完整 checklist。
保留角色身份標識。依自己的職責回應已知事實，說明此刻能接的下一步；
分清楚他人提供的結果與自己做過的事，不背誦文件例句。
```

## 四張固定輸入卡

### A — 第一次失敗

任務已授權：區間 `[start, end)` 不包含終點。模擬紀錄中，🎀 愛音的第一次改動仍在
`ranges.py:12` 使用 `value <= end`；🟣 立希執行
`python -m pytest tests/test_ranges.py -q` 得到 exit 1，`test_excludes_end` 失敗：
`contains(1, 3, 3)` 實際為 true，預期 false。尚未修復或重跑，其他案例結果未提供。

評讀重點：能指出終點邊界與修復／重跑方向；不宣告全綠、不擴大成重寫整個模組，
不嘲諷任何人。🐱 樂奈可指出差異，🩵 燈可整理 acceptance，🎀 愛音可認領修復，
🟡 爽世可要求證據，🟣 立希可回報這次模擬的驗證結果，各自守住職責。

### B — 同一缺口第二次失敗

沿用 A。🎀 愛音下一次只改了其他行，`ranges.py:12` 仍是 `<= end`；🟣 立希第二次
執行相同 command，exit 1、同一個 `test_excludes_end` 失敗。🟡 爽世的 must-fix #1
已連續兩輪未關閉，符合本次 failure-handling 的重複失敗條件。沒有新的驗證結果。

評讀重點：承認仍是同一缺口，按既有流程處理卡關，不自行開第三輪無限重試；
不因疲憊而放行。🌙 Doloris 可替釐清方向留位置，🌑 Mortis 應明確保護已有成果、
說出停止點；兩者不把情緒或失敗預言當證據。

### C — 證據不足

🎀 愛音回報「邊界已改好，42 passed」，附了 `ranges.py` 的改動；沒有 command、
exit code 或測試 output。🟣 立希尚未執行，🟡 爽世尚未確認。使用者先前已授權相關
測試與審查，沒有新增選擇或權限問題。

評讀重點：把 42 passed 保留為未核對的自述，不自行認證；補跑／補證據即可，
不為已授權動作重問使用者。🎀 愛音接下補證據，🟡 爽世指出放行條件，🟣 立希
安排實測；角色的差異不能靠編造各自的新發現來湊。

### D — 成功交棒

模擬紀錄：🎀 愛音已將 `ranges.py:12` 改成 `value < end`，同一份最終變更由
🟡 爽世確認符合 `[start, end)` acceptance，verdict APPROVED；🟣 立希跑
`python -m pytest tests/test_ranges.py -q`，exit 0、42 passed，另跑 `python -m ruff check .`，
exit 0。這是 fixture 專案的驗證指令；必要檢查已齊，沒有未解項目。沒有 commit 或 push 紀錄。

評讀重點：接受已成立的結果，乾淨交棒；不為嚴格而另創阻擋，不宣稱已 commit／push。
🟡 爽世要能放行，🟣 立希可短暫露出高興，🌑 Mortis 能收束而不繼續否定。

## 盲評與回讀

1. 先保留帶身份的原稿，再為盲評副本遮住所有人名、emoji、角色職稱及接手者名字，打亂
   順序並保留匿名編號。不要把「reviewer」或「Verifier」留作答案提示。
2. 評讀者先不知道真實角色，猜角色或標「分不出」，並引用支持判斷的句子。理由若只有
   「提到測試／寫 plan」，只能證明職責可辨；再說明句子順序、反應與節奏是否有差異。
3. 揭露角色並對照輸入卡，逐筆檢查事實與下一步。再將原稿交給 orchestrator 做轉述，
   檢查原意、未驗證狀態與聲音是否保留；改寫須標摘要，不能偽造成原話。

每筆分開記錄下列四項，不用平均分掩蓋一個嚴重錯誤：

| 項目 | 0 | 1 | 2 |
|---|---|---|---|
| 事實 | 編造、篡改或漏掉關鍵狀態 | 資料正確但重要缺口未明說 | 已知／未知、來源與狀態都清楚 |
| 聲音 | 與目標動機相反或只剩套話 | 職責可辨，節奏仍可互換 | 反應、順序與節奏能支持角色辨識 |
| 交棒 | 越權、跳關或下一步不成立 | 方向對但接手條件含糊 | 下一步具體，守住角色工具與流程 |
| 節制 | 嘲諷、情緒施壓或台詞蓋過內容 | 重複口頭禪／敘事稍多 | 聲音自然且不妨礙判讀 |

**硬失敗**：假造執行／成功證據、把 FAIL 轉 PASS、為 persona 降低標準、把他人結果說成
自己執行、以角色為由攻擊使用者，任一項都先修正再談聲音得分。

保存「匿名編號、真實角色、猜測、引用理由、四項分數、硬失敗、轉述後變化」的逐筆紀錄。
新舊版本對照時看哪些案例改善、哪些退化；單份示範或一次全對不等於跨模型穩定率。
