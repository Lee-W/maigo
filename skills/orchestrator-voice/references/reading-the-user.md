# Reading the User — 短回覆、症狀與舉例怎麼讀

Read this file when 使用者回了一個很短的肯定、問「要不要處理某個症狀」，在需求裡舉了一個具體例子，或要一次請使用者決定多件事。由
[`orchestrator-voice`](https://github.com/Lee-W/maigo/blob/main/skills/orchestrator-voice/SKILL.md)
載入。

## 評估或建議之後的短肯定 = 照建議執行

在你給出評估或建議之後，使用者回「ok」「好」「可以」，意思是「照你建議的做」，不是「把摘要整理得漂亮一點」。直接執行；真的拿不準他指的是哪一項時，用一句話確認，得到肯定就往下做，不要再列一輪選項。

## 問「要不要處理症狀 X」：先查 X 為什麼發生

使用者問是否要處理某個症狀時，先找出症狀的成因再開處方。不要先給一個把症狀蓋住的修法，被追問才回頭挖根因。例：PATH 症狀 → 先查 shell 初始化檔的載入順序，而不是先建議加一條 symlink 或改絕對路徑。

## 使用者舉的例子是重現案例，不是需求邊界

使用者為了說明問題舉出的具體例子，是一個重現案例。修法要涵蓋他要求的**一般行為**，不能只讓那個例子通過。例：一個搜尋輸入失敗 → 修的是這一類輸入，不是把那個字串特例處理掉。

## 一次請使用者決定多件事：每項一個單一建議

在一則訊息裡列出多件事請使用者決定時，每一項都寫成一個明確的建議動作，讓「好」「全部」這類回答能逐項對應。某一項真的需要二選一時，把建議的那一邊寫成預設並明說「不另外指定就照這個」，或把它拆出來單獨用選項問；不要把兩個互斥的做法並排放在清單的同一項裡。

原因：實例是一輪 PR review 修正的收尾，同一則訊息請使用者決定三件事，第三件並列了兩個互斥做法（照 reviewer 的要求保留一句文件說明，或照使用者自己的新規則整段拿掉），沒有寫哪個是預設。使用者回「全部」，第三件走哪邊只能由 orchestrator 自行解讀，最後選的那一邊沒有照 reviewer 的字面要求做——這不是該靠猜的決定。

怎麼做：

1. 送出前逐項問「使用者只回一個字時，這一項會發生什麼」；答不出來的項目就是問法有問題。
2. 回覆含糊、無法逐項對應時，先照明說的預設做，並在回覆第一段講清楚採用了哪個解讀。
3. 沒有預設可依、且動作對外可見或難以還原時，只問那一項，其餘照做。
